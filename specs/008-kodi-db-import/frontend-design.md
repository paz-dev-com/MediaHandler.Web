## (d) Open questions / items to validate

1. **US6 per-upload mapping overrides UI — confirm the deferral still stands.** The backend plan ships the `overrides` multipart field (§1.10, `PathMappingOverrideRequest`); the frontend deliberately never sends it (frontend plan §6.7; spec Open Question 1 was "include or defer?" and deferral was chosen). The backend capability will exist unused until a follow-up adds the overrides section to the launcher. Non-blocking; flag to the user for prioritization.
2. **Post-import enrichment visibility (optional UX, not contractual).** The backend auto-triggers TMDB enrichment after a successful real import (§1.6). The import UI currently gives no hint that enrichment started; the admin must look at `/admin/enrichment`. If desired, a one-line info message on the status panel/report when a real import completes ("TMDB enrichment triggered — view enrichment runs") would close the loop. Not required by the API contract; recommend only if the user wants it.
3. **Enum JSON serialization — verify at integration time.** The frontend models assume enums serialize as PascalCase strings (e.g. `"Outcome": "NeedsReview"`), consistent with how the existing scan/enrichment DTOs behave. The backend plan specifies string conversions for EF storage but does not restate the JSON serializer setting; presumably the global `JsonStringEnumConverter` applies. Smoke-test one run detail/items response when the backend is available — if numbers come back instead of strings, the frontend enums/tags/filters break (low risk, one-place fix in `Program.cs`).
4. **`GET active` idle response shape — verify.** Frontend expects HTTP 200 with `data: null` when no run is active (mirrors `GetActiveScanQuery`). Backend plan confirms `Result<ImportRunDto?>`; just confirm the controller doesn't 404 on idle.
5. **Upload `mode` parsing — verify case handling.** Frontend sends lowercase `"import"`/`"preview"`; the backend controller parses this field manually (invalid → 400 `VALIDATION_ERROR`). Confirm the parse is case-insensitive or lowercase-exact; the frontend will not change (contract fixed in the frontend plan).
6. **Pending-run `StartedAt`.** Backend DTO types `StartedAt` as non-nullable `DateTime`; the frontend's elapsed-time display guards on it. Harmless, but confirm a Pending run returns a sensible value (e.g. insertion time) rather than `0001-01-01`.

No blocking open questions for the frontend. All genuinely ambiguous items (upload transport limits, validation error codes, polling shape, counter reconciliation) were resolved by the backend plan in exactly the shape the frontend already consumes.
